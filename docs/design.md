# 设计说明

本文解释实现选择：数据模型、跨日会话的处理、封存结算与更正、竞态保护、以及可复现性。
所有数据均为虚构，代码不采集真实用户行为，也不使用任何模型打分——每条判定都能追溯到具体的检查项与阈值。

## 1. 总体流程

```
批次校验 -> raw_events（只追加）
        -> 判定：按规则版本逐事件评估 -> decision_runs + decisions + decision_contributions
        -> 分析：按当日运行头汇总 -> settlements（草稿 -> 封存）
        -> 差异：rule_compare（规则对比） / correction（证据补录更正）
        -> 审批：封存日追加 settlement_adjustments；未封存日丢弃草稿等待重算
```

每个阶段是独立进程，只通过数据库协作。判定不读取当前时间以外的外部状态：输入是原始事件行、证据行、`orderFirst` 索引和会话上下文，同一输入必然产生同一输出。

## 2. 数据模型要点

- **原始事实只追加**：`raw_events` 由触发器拒绝 UPDATE/DELETE；批次迟到、乱序都不改写历史。
- **证据只追加、按生效期匹配**：`evidence` 有 `effective_from` / `effective_to`（含端点），同一 `(kind, key)` 可以有多条不同生效期的证据；判定时按事件发生时间选出命中的那条。
- **规则版本不可变**：草稿可改，发布后 `rules_json` 被触发器冻结；删除也不允许，只能退役。规则内容有规范 JSON 摘要（`digest`），重复内容复用同一版本。
- **判定留痕**：`decisions` 保存裁决与主要理由；`decision_contributions` 为每个检查项保存 `check_order / rule_id / severity / outcome / observed / comparator / threshold / detail / evidence_ref`，网页上的“被排除原因”直接来自这里。
- **运行头**：`run_heads (stream, local_day)` 指向当日当前有效的运行；历史运行保留并标为 `superseded`。

## 3. 跨日会话怎么处理

分两层：

1. **上下文**：判定某日时，取“与当日有交集的会话”的全部事件（向前有 `lookback_days` 的回溯窗口）。所以跨午夜的转化仍能看到前一天的点击，UA / 设备 / 订单等检查也基于整段会话，不会因为跨日被误判为孤立事件。回溯窗口按 UTC 多留一天余量，覆盖本地时区偏移；窗口外的会话会在 `sessionInfo.truncated` 标记，UI 如实展示，不会假装完整。
2. **归属**：规则里的 `cross_day.attribution` 决定事件算到哪一天。
   - `attribution-day`：按事件自身发生日归属，每日各判各的；跨日会话在每个事件上都会产生一个 `cross_day_session` 贡献（默认 `note`，只记录）。
   - `session-day`：整段会话归属到会话开始的自然日，会话结束在次日的转化也计入开始日的运行；次日运行不再重复判定这些事件。
   - `cross_day.escalate_to_suspect`：为真时跨日会话的贡献从 `note` 升级为 `soft/fail`，相关事件判为 `suspect`，默认不结算。

两种模式都保证“同一事件在一次运行集合里恰好判定一次”，差异报告按事件 id 对齐两侧。

## 4. 判定规则（确定性、可解释）

硬规则（命中即 `invalid`）：点击缺少同会话曝光、点击早于曝光、点击间隔低于下限/超过上限、转化缺少点击/转化窗口超限/早于点击、重复订单号、UA 自动化特征、数据中心 IP 前缀、设备补录标记、订单撤销/退款、曝光不可见。

软规则（命中为 `suspect`）：短时事件密度过高、事件间隔过于均匀、跨日会话（可配置升级）。

每条规则都输出贡献行，包含观测值与阈值；没有模型打分，也没有无法复现的启发式。`click_delay.treat_faster_than_min_as`、`conversion_delay.orphan_click_policy` 可以把硬规则降级为可疑，这是唯一的“严重度旋钮”。结算只计 `valid`，`suspect` 需显式 `includeSuspect` 才计入。

## 5. 证据补录与“同一条事件从有效变为无效”

证据是带生效期的追加记录。新证据写入后，重新判定就会命中它，同一事件从 `valid` 变成 `invalid`。

**实现选择：保存逐条判定贡献，并以“已存库判定”为更正基线**（而不是按受影响日期重建）。原因：

- 已存库的判定就是当时结算所依据的历史，不可变；以它作基线，新证据带来的差异才能诚实地呈现为“应付 vs 已付”。
- 逐条贡献让每个变化都能下钻到具体规则与观测值，网页可逐事件核对。
- 需要重算时按日重新投递任务即可，运行历史与新结果并存，旧结果标 `superseded`，不会覆盖已封存金额。

`correction` 报告的基线来自 `run_heads` 指向的**已提交判定**（`loadStoredDecisions`），候选则用当日证据重新评估。`rule_compare` 报告不同：两侧都在**同一冻结快照**（启动时读取的接入水位 + 证据集）上重算，保证差异只来自规则本身。一次任务内所有日期共用同一快照，运行中到达的批次或证据不会渗入。

## 6. 已封存结算不可悄悄重写

- 封存后 `settlements` 行被触发器拒绝 UPDATE/DELETE；同日唯一封存记录由部分唯一索引保证。
- 封存前校验草稿依据的运行仍是当日运行头，旧草稿不能“借新运行”封存。
- 批准更正报告时：
  - 已封存日：插入 `settlement_adjustments`（`UNIQUE(report_id, settlement_id)`，本身也不可改/删），**封存金额保持原值**，页面同时展示原额、调整合计与净额。
  - 未封存日：删除过期草稿并列入 `restate`，由分析进程按最新判定重新生成，而不是在没人冻结的数字上挂调整。
- 报告一旦批准/驳回即定稿，触发器拒绝再次修改；调整分录按日幂等。

## 7. 竞态：晚结束的旧任务不能替换新结果

任务入队时分配单调递增的 `sequence`；运行头比较的是**序号**，不是完成时间。

- 旧序号任务晚完成：写入 `decision_runs` 并标为 `superseded`，任务日志记录被哪个序号覆盖，`run_heads` 不变。
- 新序号任务完成：提交并把原运行头标记为 `superseded`。
- 领取任务时 `fence + 1` 并写租约；租约过期可被回收重领。旧工作者在提交运行、写结算草稿、生成报告前后都会复查 fence，租约易主则结果整体丢弃，并以 `warn` 记录。

并发演示（两个独立进程）在 `test/process.test.mjs` 与 `npm run demo` 第 9 步中验证：先入队的慢任务最后完成，运行头仍属于较新序号。

## 8. 可复现性与审计

- 规则版本、运行、结算、调整分录、报告都保存规范 JSON 的 sha256 摘要；相同输入得到相同摘要。
- 运行记录同时保存 `ingest_watermark`、`evidence_watermark`、`as_of`、归属模式，回放时能知道它看到了什么。
- 所有写操作记录到 `audit_log`（不可改/删），网页写入使用 `EQS_OPERATOR` 署名。
- 证据按生效期匹配、判定只依赖数据行，因此任何一天的判定都可以由“原始事件 + 证据 + 规则版本”重放，不需要模型或随机数。

## 9. 接入与校验

- 每行事件由 `validateEvent` 校验：id 格式、事件类型必填字段、IPv4、带时区的 ISO 时间、`received_at` 不早于 `occurred_at`、`revenue_cents` 非负整数等。
- **整文件通过才写库**；失败时记录 `ingest_files.status = 'failed'` 与错误行号，`raw_events` 零写入。
- 文件按名称 + 内容摘要去重：同文件重复投递跳过；同名不同内容拒绝并要求改名。
- `event_id` 冲突按“首次摄入为准”；重复订单号同样以最小 `ingest_seq` 为首次。

## 10. 时区

事件归属使用 `Intl.DateTimeFormat` 按配置时区（默认 `Asia/Shanghai`）计算本地日，不依赖服务器时区。会话回溯窗口按 UTC 额外留一天余量，避免本地日边界落在窗口外。

## 11. 网页

无构建步骤的原生 ES 模块页面（`web/public`），由 `web/server.mjs` 提供静态文件与 `/api/*`。图表为手写 SVG：2–3 色分类配色、图例、悬停提示、数据表副本、明暗两套色值（深色是单独选值，不是自动反转）。数值使用等宽数字，金额统一按“分 → 元”格式化。所有列表数据来自上面所述的运行/判定/结算表，页面不自行造数。
